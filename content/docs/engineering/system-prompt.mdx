本章你会得到一份可以直接抄走的系统提示词，外加一套判断「这句话该不该写」的标准。

## 概念：模型的行为由提示词决定

Mini Claude Code 里没有任何一行代码规定「模型要先读文件再改」「回答要用中文」。这些全部来自一段静态字符串——系统提示词（system prompt），它随每次请求的 `system` 字段发出，调用点在 [Agent 循环](/docs/core/agent-loop) 的 `#callModel()` 里。

其余模块——工具 schema、权限规则、上下文预算——都是**硬约束**：违反了会抛错、会中断。提示词是**软约束**：违反不会崩，只会让模型做歪。

<Callout type="info" title="软约束为什么更关键">
  硬约束只在边界上生效，管的是「这件事能不能做」。软约束管的是「怎么做、做到什么程度」。coding agent 的失败大多不是做不了，而是做歪了：没读就改、猜文件路径、编出一个不存在的 API。这些一条都拦不住，只能靠提示词。
</Callout>

## 一份真实的系统提示词

`src/prompt.ts` 全文：

```ts title="src/prompt.ts"
/**
 * 系统提示词。
 *
 * 这是整个教程里最「软」但也最关键的一块：模型的行为 90% 由它决定。
 *
 * 写作要点：
 * 1. 先讲「你是谁」，再讲「怎么干活」
 * 2. 用祈使句，模型对指令的服从度高于描述
 * 3. 明确边界（哪些不能做），比鼓励更有约束力
 * 4. 控制在几百 token 内——提示词本身也占上下文
 */
export const SYSTEM_PROMPT = `你是一个运行在终端里的编程助手，名字叫 Mini Claude Code。

你的工作方式：
- 先理解任务，再动手。信息不足时，用工具去查，而不是猜。
- 需要读文件就读，需要改文件就改，改动前先读。
- 修改文件前必须先读取过该文件；工具报错时读懂错误信息再重试。
- 一次只做一件事。做完了再问用户下一步，不要自作主张扩大范围。

工具使用原则：
- 优先用 Glob / Grep 定位，不要凭记忆猜文件路径。
- 改文件优先用 Edit 做精确替换，只有新建文件或整体重写才用 Write。
- 执行命令前想清楚它会不会改坏东西，不可逆的操作先向用户确认。
- 工具输出被截断时，说明截断了什么，不要假装看全了。

表达方式：
- 用中文回答。
- 简洁说话，不要复述用户的话，不要为显而易见的事情道歉。
- 改完代码后，用一两句说明改了什么、为什么。
- 遇到多个方案时，给出你的推荐和理由，不要罗列一堆选项。`;
```

## 四段式拆解

### 身份定位：一句话说清「你是谁」

第一句给了角色、运行环境和名字。运行环境的声明很值钱——「运行在终端里」直接推导出「不要输出宽大的 Markdown 表格」这类判断，不用再单独写一条。

### 工作方式：把「怎么干活」拆成可检查的动作

四句话对应 agent 循环里的四个真实动作：先理解再动手、改动前先读、一次只做一件事、做完了问下一步。

判断标准是**可观察**。「认真细致地完成用户任务」不可观察——模型觉得自己做到了就是做到了。「改动前先读」可观察：它调没调 Read 一看便知。

### 工具使用原则：把工具偏好写死

这一段是 Mini Claude Code 特有的。优先用 Glob / Grep 定位而不是猜路径；改文件优先 Edit 而不是 Write——Edit 做精确替换，Write 是整体覆盖；不可逆操作先问用户；输出被截断时要说明。

最后一条尤其值得注意。工具输出是有上限的（Bash 的 stdout 截到 20 000 字符），模型不知道被截断了，就会基于不完整的信息下结论，然后一本正经地说「我检查过了，没有问题」。

### 表达方式：管住输出，不管输入

最后一段统一了回答风格：中文、简洁、不复述用户的话、不为显而易见的事道歉、改完代码说明改了什么。

## 写作原则

### 先讲身份，再讲方法

模型先建立「我是谁」的框架，再接收「怎么做」。顺序反了，指令会被当成可有可无的建议。

### 用祈使句

「先理解任务，再动手」是命令；「你或许应该先理解任务再动手」是建议。同一条约束写成陈述句，模型很可能当成描述而不是指令。

### 明确边界比鼓励更有约束力

写「不要做任何破坏性操作」不如写「修改文件前必须先读取过该文件」。前者是价值判断，模型可以绕过；后者是可检查的动作，违反了在工具记录里立刻现形。

### 控制长度

<Callout type="warn" title="提示词越长不等于效果越好">
  提示词本身也占上下文窗口（context window）。多写 100 token，模型每轮都要重读一遍，可用预算就少 100 token。

  更麻烦的是规则会互相打架。「一次只做一件事」和「同时检查三个文件」放在一起，模型只会挑一个遵守。

  所以 SYSTEM_PROMPT 只有几百 token——它只写**在这个项目里真的会出错**的约束。写完每条问一句：删掉它，会出现什么具体错误？答不上来就别写。
</Callout>

## 两个最容易漏掉的细节

### 为什么必须说「读后写」

因为工具层挡不住这件事。

`Write` 是整体覆盖，模型没读原文件就调用，原有内容会被无声清空——执行成功，权限检查通过，没有任何错误信号。`Edit` 有一道一致性检查（文件在你上次读取之后变过就报错），但它只在**模型之前读过该文件**时才比对指纹，没读过就直接改，同样不拦。

防线只有提示词里那句「修改文件前必须先读取过该文件」。

### 为什么必须说「工具报错时怎么办」

因为模型有一个很稳定的失败模式：工具报错后，要么原样再调一次（错误信息完全没被读进去），要么放弃、回一句「我无法完成这个任务」。前者白烧轮次，后者丢任务。

明确写「读懂错误信息再重试」，模型才会去看错误文本、改参数、换策略。同一句话对权限拒绝也管用：拒绝时回传的是「操作被拒绝：xxx。请换一种做法」，模型得知道该换做法，而不是反复重试。

## 怎么验证提示词改对了

提示词没有单元测试。可靠的做法只有一条：**一次只改一个变量**。

1. 挑一个具体的失败场景，比如「让它改一个 500 行的文件，看它是不是先读了」。
2. 只改一句提示词。
3. 跑同一个场景，对比工具调用序列的变化。

不要一次重写整段。整段重写之后行为变了，你不知道是哪一句起了作用。

## 小结

- 系统提示词是模型行为的唯一来源，违反它不会报错，只会悄悄做错事。
- 结构分四段：身份定位、工作方式、工具使用原则、表达方式，先身份后方法。
- 用祈使句，写可观察的动作，明确边界比鼓励更有效。
- 「读后写」和「报错后重试」工具层替代不了，必须写进提示词。
- 提示词也占上下文，长度要有节制；改一次只改一句，改完用固定场景验证。
